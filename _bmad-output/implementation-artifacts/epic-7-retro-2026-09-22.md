### Aggregate views

**A1 — Publish ordering: the shell document could be published before its own subresources. (BLOCKER, fixed).**
`spec-7-2` line 34 states, as a frozen *Always* obligation, that "the pipeline publishes tree-first". The shipped workflow published the whole shell with one unordered `aws s3 sync` (`a0266bc:.github/workflows/sync-game-release.yml:116`), and the runtime grants `immutable, max-age=31536000` on URL shape alone while selecting the R2 object from the path (`src/lib/engine-addressing.ts:87-92`, `src/app/engine/[...path]/route.ts:219` — the query is not part of the key). A client that booted inside the window where `engine/index.html` was already the new release while a subresource key still held the previous release's bytes cached those old bytes **under the new `?v=` URL, immutably, for a year** — and `immutable` suppresses revalidation on reload, so the mixture was permanent for that client until the next release changed every URL. The deferred-work entry filed this window as "bounded and self-healing on the next document load"; it was neither.
*Fixed:* the shell publish is now two ordered syncs — every object except `index.html` first, `index.html` alone last (`sync-game-release.yml`, "Synchronize Engine Shell to Private R2"); `tests/workflow-manifest.test.ts` pins the order; `AGENTS.md`, `engine-browser-compat.md` §2, `save-and-runtime-contract.md` §5 and the deferred-work entry carry the reason; `spec-7-2` has a dated amendment.

**A2 — God-file growth. (accepted, noted).** `src/engine-plugins/Ropoductions_WebBridge.js` grew 309 → 1206 lines (+897) across 7.1 and 7.4; `src/components/game-viewport.tsx` 396 → 770. Nothing forced the split: the plugin is injected as plain JS with no bundler, so boot classification, retry policy, WebGL probe, bitmap hooks and XHR hooks necessarily live in one file, and the host half is one client component. Recorded so the next touch is deliberate: split the plugin into boot/retry/save sections at the next engine-plugin story.

**A3 — Duplication map. ### Lens findings — Story 7.1 (classification and recovery surface)

**B1 — A loaded document with no boot script was treated as the mock harness. (fixed).** `game-viewport.tsx` returned silently whenever the frame's document had no `main.js` `script[src]`, with a comment asserting it was the website-owned harness. An error body — the shell route answers 403/404/500 as JSON — is same-origin, loads, and has no boot script, so the player got a dismissed loading overlay and a blank frame with **no recovery surface and no paywall escalation**, the exact class of outcome 7.1 exists to eliminate. *Fixed:* the harness is now recognised by an explicit marker (`src/engine-plugins/mock-shell.html` carries `meta[name="ropoductions-harness"]`), and anything else without a boot script reports `boot_request_failed` naming the document URL and its script inventory; `e2e/engine-boot-error-document.spec.ts` covers it end to end.

**B2 — `isSafeEngineSrc` accepted cross-origin and protocol-relative sources. (fixed).** It only rejected `javascript:`/`data:`/`blob:` and then accepted anything starting with `/`, `http://` or `https://` — including `//tracker.example/engine/index.html`, which starts with `/`. No attacker-controlled path exists today (`/play` passes a constant), so this was a latent guard, not an exploit; the frame it embeds would also have had its reports discarded by the source check, producing a false boot failure. *Fixed:* `isSameOriginEngineSrc(value, baseOrigin)` resolves against the origin and requires equality; unit-tested for eight shapes.

**B3 — The watchdog's boot-script probe had no deadline. (fixed).** The probe's only abort signal was unmount/retry, and the watchdog is one-shot, so a stalled probe consumed the boot budget with the overlay already dismissed: silence as the final state. *Fixed:* a 5s deadline reports `boot_request_failed` with `networkError: "boot script probe timed out"`, distinct from the unmount abort.

**B4 — The WebGL preflight probed `webgl2` first. (fixed).** `runWebglProbe` asked for `webgl2` and fell back to `webgl`, while MZ's gate (`Utils.canUseWebGL`) asks for `webgl` only — so a WebGL2-only answer passed the parent gate and then failed the engine's own capability check, breaking the "no request when MZ would refuse" contract the story's own docstring claims. *Fixed:* the probe asks for exactly `webgl`.

**B5 — A non-array `engineScripts` could crash the recovery rendering. (fixed).** `isEngineBootFailureReport` validated the envelope only, and `buildDiagnosticsReport` kept any string, so `diagnostics.engineScripts` as a string survived into `engineBootDiagnosticsRows`, which maps it — a `TypeError` inside the panel that is supposed to be the failure surface. The parser's own contract says a malformed payload "is ignored without changing any state". *Fixed:* the boundary keeps `engineScripts` only as a string array, with unit cases for both shapes.

**B6 — `markEngineReady` unconditionally clears a reported failure. (rejected).** The READY report is the story's declared boundary that closes the boot window; a READY after a reported failure means the engine did reach readiness, and the plugin stops reporting past it. Dismissing the panel is the intended behaviour, not a defect.

**B7 — Minor, deferred.** An unparseable boot-script URL returns silently (`game-viewport.tsx:221-224`); duplicate reports for one asset can carry a relative and an absolute URL in the dedupe key. Both are diagnostic-quality issues on paths that already report something else; recorded for the next boot-surface touch.

### Lens findings — Story 7.2 (release addressing)

**B8 — Silent unaddressing when a staged reference already carried a query or fragment. (fixed).** `addressDocument` appended `?v=<id>` to the whole captured value, so `src="js/main.js?a=1"` became `js/main.js?a=1?v=<id>` and `src="js/main.js#frag"` became `js/main.js#frag?v=<id>`; in both cases the browser sends no usable `v`, the runtime treats the request as unaddressed and serves `private, max-age=86400`, and the publish reports success because the strict count matches the lenient hint count. *Fixed:* the identifier is inserted into the query, before any fragment (`?theme=dark&v=…`, `js/main.js?v=…#frag`), the addressed-reference count accepts either separator, and `tests/engine-addressing.test.ts` pins the case. No real shell reference carries a query today — this closes the failure mode before upstream adds one.

**B9 — Arbitrary or stale `?v=` values are granted the immutable cache. (accepted).** The runtime is release-agnostic by owner decision (OD-2b): it applies a cache policy to the URL shape and serves the object the path names. The dangerous half of that — a stale URL aliasing a newer object while the client caches it immutably — is what A1's ordering fix closes for the pipeline's own window. A caller fabricating a 64-hex value only poisons its own cache.

**B10 — The scanner sees `src`/`href` only, three source files, case-sensitive attributes; the anchored regexes can match a comment. (accepted, one deferred).** Any reference the pipeline does not address degrades to a revalidation by design; the real-shell verification found exactly one such reference (`fonts/Minicode.json`, plugin-authored). The fail-open validation hole (a retained comment matching an anchor rule while the executable site changed) is deferred hardening.

**B11 — A previously published `engine/build-metadata.json` stays in the bucket. (accepted).** The additive sync never deletes, so the object from the pre-7.2 pipeline remains; it is unreachable (`sanitizeAssetPath` rejects a non-allowlisted top-level segment with 400 before any R2 access, pinned by a test). The wording is corrected where it claimed the file is published nowhere.

**B12 — A valid document with unquoted attributes would fail the run. (accepted).** The strict scanner requires quotes while the lenient hint does not, so an unquoted shell reference aborts the publish. Fail-closed is the intended direction for a shape the rules do not recognise.

### Lens findings — Story 7.3 (burst-safe validation)

**B13 — Independent security pass: clean.** A dedicated security review read the memo, its call sites, both route handlers, the tests and the rewrites and returned **zero** findings. Verified closures, each with a code reference: every strict-rejectable state that a hit can still serve (revoked-after-verdict, `override_deleted`, pledge-floor loss) is bounded by the earlier of the monotonic window deadline and the verdict's own `expires_at_sec`, both re-checked per hit (`session-validation-memo.ts:148-157`); `lapsed`, `not_found` and `invalid_signature` are never stored and never served; the key is a full-length 32-byte SHA-256 digest of `secret:cookie` with no truncation, so a rotated secret misses every entry and cross-session reuse needs a collision; nothing retains or returns the session record, its id, the cookie or a token (`Resolution` holds a number or a denial); a forged-cookie flood creates only transient pending entries that settle without a D1 read (the signature check precedes the read) and self-deletes; the retained store is bounded and evicts settled entries only; anonymous traffic costs zero reads. 21/21 focused cases pass.

**B14 — Pending entries are unbounded and retain the request's cookie. (accepted residual, wording work outstanding).** In-flight validations are deliberately never counted or evicted, so the honest bound is the runtime's in-flight concurrency and request lifetime, and a validation that never settles pins its closure — including the cookie — until it does. The spec records this as an accepted residual (SEC-73-POST-03). The contract wording that reads as a hard store bound still needs tightening (action item 6); only a validly signed cookie reaches a D1 read at all, so the exposure needs a hung D1 with real sessions in flight.

**B15 — `reset()` did not invalidate in-flight completions. (fixed).** The store is process-global while the route suites swap the D1 binding, so a validation started before `resetSessionValidationMemo()` could settle afterwards and write its pre-reset verdict back into the fresh store — exactly the cross-fixture leak the seam exists to prevent. *Fixed:* the memo carries a generation captured before its first `await` (capturing it after the key hash left a window in which a pre-reset request still registered), `reset()` bumps it, and both the registration and the settle mutate nothing when their generation is stale. Verified red-first: with the guard removed the new case fails with the cleared store holding a key.

**B16 — Hits do not refresh eviction recency; an A→B→A secret rollback can reuse an old entry. (rejected).** Eviction order is not correctness: an evicted session simply revalidates. A rollback that restores the previous secret within the window reuses a verdict that was authorized under that same secret and is still inside its window.

### Lens findings — Story 7.4 (asset-load retry)

**B17 — A bitmap was stranded in `loading` when readiness closed its retry window. (fixed).** The scheduled retry callback returned silently under `if (bootReady) return`, so a bitmap whose retry landed after the READY report never reached MZ's terminal `error` state and nothing reported it — the sprite stays broken for the session with no surface. Two independent lenses found it. *Fixed:* that branch now calls `finishBitmapFailure`, which sets `_loadingState = "error"` (the host report stays suppressed past readiness); covered by a case in `tests/engine-asset-retry.test.ts`.

**B18 — The retry budget was not per URL. (fixed).** The documented contract is "at most 2 attempts per URL per boot": any bitmap success deleted the URL's counter (so two concurrent bitmaps for one URL could each spend a fresh budget), and every XHR kept its own counter (so two requests for one URL could spend four). One implementation now enforces the contract for both paths — the bitmap counter is never reset inside the boot window and the XHR path shares the same per-URL counter.

**B19 — `401`/`403` images are retried when Resource Timing has no status. (accepted).** An `<img>` element carries no status, so `responseStatus` is the only evidence; its absence means "the request never completed", which the spec records as retryable, including in browsers without the property. The cost is two wasted attempts and a `boot_request_failed`/`asset_load_failed` panel instead of a session escalation — narrow, and it needs a browser that does not expose `responseStatus`.

**B20 — Deferred.** Aborts and timeouts on retry-owned XHRs are not wrapped (an abort during a backoff still re-issues the request; `ontimeout`/`onabort` never clear the retry state); a replayed MZ handler that throws escapes the wrapper; a failed `<img>` may read a stale Resource Timing entry for the same URL.

**B22 — The burst and reload specs cannot prove the amortisation they claim. The unit-level proof existed but was sequential too. *Closed in substance on the merged code:* `tests/engine-route.test.ts` now fires 12 concurrent shell requests through the real handler against a counting D1 and asserts one session read, alongside route-level cases for "validation failure answers 500, never implicit authorization" and "requests answered before validation cost zero reads" in both route suites. The fixture-based e2e profile itself (`fixtureBody` returns a comment) is a recorded limitation: it proves the cache and addressing contracts, not that MZ executes.

**B23 — The WebGL-disabled spec asserted shared copy, not the class. (attribute added; assertion remains 7.5's).** `webgl_unavailable` and `renderer_init_failed` render identical player copy, so a classification regression was invisible. The panel now exposes `data-failure-class`, and the new e2e case asserts it; asserting it under a genuinely WebGL-disabled Firefox profile stays with PR #60 because that spec lives on 7.5's branch.
